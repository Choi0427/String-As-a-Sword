0. 적용할 스킬과 기능별 커밋 규칙

작업 시작 시 현재 환경에서 제공되는 스킬 목록과 프로젝트 지침을 확인하고, 다음 스킬의 SKILL.md 및 필요한 참조 가이드를 읽어 적용해주세요. 스킬 이름만 언급하지 말고 실제 작업 방식과 검증에 반영하세요.

- unity: Unity 전투·입력·오디오·채보 연동·렌더링·테스트 구현에 사용하세요. Unity MCP/CLI를 사용할 때는 unity-cli 가이드를 확인하고 실제 프로젝트의 에디터 버전과 연결 상태를 확인하세요. 예고 시각화는 현재 렌더링 구조를 유지하며, Canvas/TextMesh Pro를 사용하는 부분은 ui 및 ui-ugui 관련 가이드를 적용하세요.
- ponytail (full): 기존 전투·채보·입력·테스트 구조를 재사용하고, 요구사항을 모두 충족하는 가장 작은 변경을 선택하세요. 간소화를 이유로 아래의 공정성 규칙, 데이터 편집 기능, 재현성, 시뮬레이션, 자동 테스트 또는 실제 화면 검증을 생략하지 마세요. 실제 플레이와 시뮬레이션이 공유해야 하는 로직은 필요한 범위에서 분리하세요.
- ponytail-review: 각 기능의 마무리와 최종 통합 검토에 사용하세요. 검토 범위를 이번 작업의 변경 파일·커밋으로 명시하고, 변경된 함수의 호출부·설정·테스트까지 확인하세요. 특히 노트 판정 종료 순서, 미래 정보 접근, 결정론, 탐색 비용, 채보 편집·선택 회귀를 점검하세요. 리뷰에서 확인된 문제는 구현 단계에서 수정한 후 필요한 검증을 다시 수행하세요.

추가 스킬은 실제 작업에 도움이 되는 경우에만 선택하세요. 예를 들어 예고·HUD의 대비, 숫자 배치, 중첩 표시를 점검할 때는 사용 가능한 경우 impeccable을 보조적으로 적용할 수 있습니다. 지정 스킬이 없으면 그 사실을 알리고 사용 가능한 지침과 도구로 진행하되, 검증하지 못한 부분을 명시하세요.

사용한 스킬과 적용 목적을 작업 시작 또는 해당 스킬을 처음 적용할 때 짧게 알리고, 최종 보고에도 기록해주세요. 스킬의 일반 지침과 이 프롬프트의 명시적 요구가 충돌하면 이 프롬프트의 요구를 우선하세요. 진행 설명과 최종 보고는 한국어로 작성해주세요.

기능을 구현할 때마다 다음 절차로 커밋 메시지와 변경 이력을 남겨주세요.

1) 먼저 AGENTS.md, 저장소의 커밋 지침, 최근 커밋 형식을 확인하세요. 별도 규칙이 없으면 기존 형식에 맞춰 feat:, fix:, test:, docs:, refactor: 접두어를 사용하세요.
2) 독립적으로 설명하고 검증할 수 있는 기능 단위로 작업을 나누세요. 예를 들어 전투 판정·피격, 보스 패턴, 예고 시각화, 공정한 잡음 생성, 로그·재현, 시뮬레이션·HP 산정처럼 구분하되 실제 코드 의존성에 맞게 조정하세요.
3) 각 기능의 구현과 관련 검증을 마친 시점에 이번 작업에 해당하는 파일만 선별해 로컬 Git 커밋을 만드세요. 기존 사용자 변경사항을 함께 커밋하지 마세요. 서로 무관한 기능을 마지막에 한 커밋으로 합치지 마세요.
4) 커밋 제목에는 구현한 동작을 구체적으로 쓰고, 필요한 경우 본문에 변경 이유, 수행한 테스트와 결과, 남은 제약을 기록하세요. 아직 실행하지 않은 검증을 통과한 것처럼 적지 마세요.
5) 각 기능을 마칠 때 커밋 해시와 메시지를 짧게 알리세요. 커밋을 만들 수 없다면 이유, 대상 파일, 작성한 커밋 메시지 초안을 남기고 실제 커밋과 구분하세요.
6) 최종 결과에 '기능 / 커밋 해시 / 커밋 메시지 / 검증 결과' 표를 추가하세요. 사용한 스킬과 적용 목적도 함께 정리하세요.

커밋 메시지 예시:

- feat: select noise spawn cells using reachable safe routes
- feat: calibrate boss health from Original action budgets

1. 목표와 보존 범위

목표는 344개의 행동 기회 안에서 잡음을 수집하고 보스를 처치하는 전투입니다. 이동·방어·공격 횟수에 개별 제한을 거는 것이 아니라, 실제 플레이 경로에서 필요한 비용을 측정해 HP를 결정합니다.

다음 기존 규칙을 유지해주세요.

- Original: 87 BPM, 344개 노트, 기존 노트 위치와 판정 설정 유지.
- 한 노트에는 이동·공격·방어 중 하나만 인정.
- 8×8 보드에서 상하좌우 한 칸 이동.
- 최상단 행에서만 보스에게 피해 1.
- 최상단 밖의 공격은 행동을 소비하지만 피해를 주지 않음.
- 잡음은 기존 음악 박자 기준 8박 간격, 동시에 최대 2개.
- 이동으로 잡음이 있는 칸에 도착하면 수집.
- 1~3페이즈 수집 목표는 3·4·5개, 4페이즈는 수집 없음.
- 해당 페이즈의 HP 소진과 수집 목표를 모두 충족해야 전환.
- 기존 페이즈 전환 시 잡음 초기화 규칙 유지.

Original과 Special을 포함한 모든 채보의 편집·선택 기능을 보존하세요. 보존은 편집 금지를 뜻하지 않습니다. 이번 구현에서 채보를 임의로 재생성하거나 수정하지 마세요.

344개와 87 BPM은 이번 밸런스 측정 대상의 값입니다. 공용 전투 코드에는 이를 고정값으로 넣지 마세요. 음악 박자와 채보 노트 인덱스의 구분도 유지해주세요.

현재 플레이어 피격이나 방어 효과가 미구현이라면 아래 규칙으로 추가하세요.

2. 방어·피격·종료 규칙

- 방어는 인정된 해당 노트의 일반 보스 공격을 막고 위치를 유지합니다.
- 방어 효력은 애니메이션 길이가 아니라 판정된 노트에 귀속됩니다.
- 키를 누르고 있는 것만으로 연속 방어되지 않게 기존 입력 방식을 유지합니다.
- 회피는 공격 범위 밖으로 이동하는 것입니다. 회피 이동으로 잡음을 동시에 수집할 수 있습니다.
- 초기 패턴은 모두 방어 가능하게 구현합니다.
- 같은 노트에 여러 공격이 겹쳐도 체력 손실은 최대 한 번입니다.
- 초기 버전에서는 피격 밀치기를 추가하지 않습니다.
- Miss 자체에는 추가 체력 피해를 주지 않습니다. 해당 노트에 보스 공격을 회피·방어하지 못했다면 피격됩니다.
- 플레이어 최대 HP는 편집 가능한 설정으로 두고, 초기 테스트값은 3으로 시작합니다. 확정된 밸런스값으로 표현하지 마세요.

보스 공격은 해당 노트의 판정 창이 닫힌 후, 그 노트에 인정된 이동·방어를 반영해 판정해주세요. 정상적으로 인정된 늦은 Good 입력이 피격 판정에서 무시되면 안 됩니다.

기존 이동·수집 반응성을 유지하면서, 다음 사건의 처리 순서를 명확히 정하고 테스트하세요.

- 플레이어 행동과 수집
- 플레이어의 보스 공격
- 보스 공격과 플레이어 피격
- 페이즈 전환
- 사망·승리·시간 초과

동시에 마지막 공격과 피격이 발생하는 경우의 우선순위도 문서화하세요. 페이즈 전환 과정에서 예고 없는 공격이 생기지 않도록 하세요.

마지막 노트 판정 종료 시 보스를 처치하지 못했다면 시간 초과로 구분하세요. 단순한 채보 재생 완료를 승리로 처리하지 마세요.

3. 보스 패턴

첫 버전은 다음 세 종류를 데이터로 편집할 수 있게 구현해주세요.

A. 행·열 공격
- 지정한 행 또는 열을 예고한 뒤 공격합니다.
- 방어로 자리를 지키거나 이동으로 피할 수 있습니다.

B. 위치 고정 공격
- 예고 시작 시 플레이어 위치를 대상으로 고정합니다.
- 예고 이후 플레이어를 추적하거나 범위를 변경하지 않습니다.

C. 최상단 압박
- 공격 가능한 최상단 행의 일부를 공격합니다.
- 안전한 공간과 도달 가능한 회피 경로를 남깁니다.
- 옆으로 이동, 방어, 잡음 수집을 위한 이탈 중 판단할 여지가 있어야 합니다.

초기 예고 길이는 2~4노트를 시험값으로 사용하되, 이동에 필요한 행동 수보다 대응 시간이 부족하지 않도록 검증해주세요.

패턴별 범위, 예고 길이, 발동 노트, 반복 간격, 페이즈별 사용 여부를 편집 가능하게 만드세요.

패턴이 겹칠 때는 합쳐진 공격 범위를 기준으로 안전성을 검사하세요. 나중에 추가된 패턴이 이미 공개된 예고에 대한 합리적인 대응을 무효화하지 않도록 하세요.

매 노트 공격을 발생시키는 것이 목표는 아닙니다. 압박 사이에 수집·복귀·공격 기회를 배치하고, 각 행동이 이후 공격 기회에 영향을 주도록 구성해주세요.

4. 반드시 구현할 예고 시각화

보스 공격 예고는 흰색 대각선 빗금과 명확한 테두리로 위험 칸을 구분해주세요.

다음 조건을 모두 만족해야 합니다.

- 플레이어가 서 있는 칸에도 예고가 확실히 보입니다.
- 플레이어·잡음·이펙트가 겹쳐도 위험 영역과 남은 노트 수를 식별할 수 있습니다.
- 예고 때문에 플레이어의 위치와 형태를 알아보기 어려워지면 안 됩니다.
- 밝은 바닥에서도 흰색 빗금이 보이도록 어두운 받침이나 외곽선을 사용합니다.
- 투명도만 낮춰 표시하는 방식에 의존하지 마세요.
- 보드 위 빗금, 테두리, 숫자의 렌더링 순서를 명시적으로 관리합니다.
- 현재 카메라 각도와 실제 게임 화면에서 읽을 수 있어야 합니다.
- 예고 상태와 실제 공격 발동 상태를 빗금 밀도·테두리·문구 등으로 구분합니다. 색상만으로 구분하지 마세요.

각 위험 칸에는 남은 노트 수를 읽을 수 있게 표시하고, 패턴 단위로도 “공격까지 N노트”를 확인할 수 있게 해주세요. 표시가 중복되어 복잡해지면 동일 패턴의 대표 문구와 칸별 숫자를 조합하세요.

남은 노트 수의 의미는 아래처럼 통일합니다.

- 활성 채보의 노트 판정 완료를 기준으로 계산합니다.
- 입력 횟수, 프레임, 초, 음악 박자 수로 대신 계산하지 않습니다.
- 한 노트 판정이 완료될 때 정확히 한 번 감소합니다.
- Miss여도 감소하고 일시정지 중에는 멈춥니다.
- 1은 다음 노트 판정 종료 시 발동한다는 의미입니다.
- 발동 순간은 “공격!” 또는 명확한 기호로 구분합니다.
- 내부 인덱스와 사용자에게 보이는 노트 번호를 혼동하지 마세요.

예를 들어 마지막으로 판정을 완료한 노트 인덱스를 기준으로
남은 노트 수 = 발동 노트 인덱스 - 마지막 판정 완료 노트 인덱스
처럼 일관된 규칙을 사용하고 경계 조건을 테스트하세요.

한 칸에 발동 시점이 다른 예고가 겹친다면 가장 임박한 공격과 추가 예정 공격이 있음을 함께 표시하세요. 숫자를 단순히 겹쳐 그리지 마세요.

5. 공정한 잡음 생성

기존 생성 간격·최대 개수·수집 목표를 유지하면서, 유효한 후보 안에서 시드 기반 무작위로 위치를 선택해주세요.

후보 판정은 단순 거리만 보지 말고 다음을 고려해야 합니다.

- 공개된 공격 예고를 고려한 시간별 안전 경로
- 수집에 필요한 이동·방어·대기
- 수집 후 최상단으로 복귀하는 비용
- 남은 목표 수집과 공격을 수행할 행동 예산
- 기존 잡음 두 개가 접근 불가능한 상태로 생성 한도를 막는 경우

회피와 수집을 동시에 수행하는 이동은 한 번으로 계산하세요.

이미 생성된 잡음을 플레이어의 선택에 맞춰 옮기지 마세요. 이미 확정한 예고 범위도 변경하지 마세요.

유효 후보가 없다면 무기한 생성 실패로 남기지 말고, 제한된 연기와 안전한 대체 위치 선택 절차를 정의하세요. 기존 음악 박자 기준을 어떻게 유지하는지도 명시하고, 적용된 대체 처리는 로그에 남기세요.

항상 가장 가까운 칸만 선택하지 말고, 안전성을 만족하는 후보 안에서 다양한 동선이 나오게 하세요.

공정성은 모든 잘못된 선택을 구제한다는 뜻이 아닙니다. 공개된 정보로 합리적으로 판단할 수 있는 대응 경로가 있는지 검증하세요. 미래의 무작위 결과를 미리 알아야만 성공하는 배치는 허용하지 마세요.

6. 행동 로그와 재현성

실제 플레이와 시뮬레이션은 가능한 한 같은 전투·생성·판정 로직을 사용해주세요. 별도의 단순화된 시뮬레이터만 통과하고 게임에서는 다르게 동작하는 구조를 피하세요.

각 실행에서 다음 정보를 기계적으로 분석 가능한 형식으로 기록해주세요.

- 시드, 채보 식별자와 내용 해시, 전투 설정 버전
- 노트 번호와 음악 박자
- 행동, 입력 판정, 행동 전후 위치
- 공개된 공격 예고와 발동 시점
- 보스 공격, 방어 성공, 피격 원인
- 잡음 생성·수집·생성 연기 및 대체 처리
- 유효 공격, 실제 피해량, 페이즈 HP
- 이동·방어·공격·기타 누계
- 페이즈 전환 노트, 종료 결과

노트별 행동은 상호 배타적으로 분류하세요.

전체 판정된 노트 수 = 이동 + 방어 + 유효 공격 + 기타

기타에는 Miss, 대기, 헛공격 등 피해를 주지 못한 기회가 포함됩니다. 세부 원인을 별도로 기록하세요.

전체 채보를 끝까지 분석한 실행에서는 합계가 344가 되어야 합니다. 조기 사망·클리어로 종료된 실행에서는 처리한 노트 수와 남은 기회를 별도로 기록하고, 합계를 억지로 344로 맞추지 마세요.

실제 피해량과 공격 가능한 기회도 구분하세요. 페이즈 HP가 이미 소진되어 무효화된 공격을 공격 능력이 부족했던 것으로 잘못 집계하지 마세요.

같은 버전·설정·시드·입력 기록으로 같은 결과를 재현할 수 있어야 합니다.

7. 시뮬레이션과 HP 산정

Original 채보를 대상으로 아래 전략을 비교해주세요.

- 수집 우선: 안전하게 수집한 뒤 공격 위치 복귀
- 공격 유지: 최상단을 유지하며 방어하고 수집 시점 조절
- 이동 활용: 회피·수집·복귀를 같은 이동으로 해결

HP 산정용 플레이어는 현재 공개된 정보만 사용해야 합니다. 미래 난수나 미공개 패턴에 접근하지 못하도록 분리하세요.

전지적 탐색은 해결 경로의 존재를 검사하는 보조 수단으로만 사용하세요. 제한된 탐색에서 경로를 못 찾은 결과를 불가능하다는 증명으로 표현하지 마세요.

최소 이동 횟수와 최소 방어 횟수를 독립적으로 구해 344에서 빼지 마세요. 같은 실행 경로에서 함께 측정한 행동량을 사용해야 합니다.

HP와 페이즈 전환 시점의 순환 의존은 다음 순서로 처리해주세요.

1) 분석 전용 모드에서 페이즈별 공격 가능량을 측정합니다.
2) 측정값으로 HP 후보를 만듭니다.
3) 실제 HP·수집 조건에 의한 페이즈 전환 규칙을 적용해 전체 곡을 다시 실행합니다.
4) 전환 시점이 바뀌어 예산이 달라지면 반복 보정합니다.

분석 전용 모드의 가상 페이즈 구간을 실제 게임의 강제 전환 규칙으로 넣지 마세요.

임시 목표 구간은 다음을 출발점으로 사용하세요.
- 1페이즈: 1~80번 노트
- 2페이즈: 81~168번 노트
- 3페이즈: 169~264번 노트
- 4페이즈: 265~344번 노트

이는 음악 구간을 검증한 결과가 아니라 초기 예산 가설입니다. 실제 음원이 연결되어 있지 않다면 후렴 등의 음악적 구간과 일치한다고 주장하지 마세요.

HP 산정에는 다음을 포함해주세요.

- 전략별·페이즈별 이동, 방어, 유효 공격, 기타의 분포
- 시드에 따른 편차
- 페이즈 전환 시점
- 실패 원인과 목표 미달 여부
- HP 산식과 여유분
- 선택한 HP로 다시 측정한 전체 클리어 결과

첫 후보는 기준 플레이어 공격량의 하위 10% 지점에서 10~15%의 여유를 남기는 방식으로 산정할 수 있습니다. 기준 전략, 분위수 계산과 정수 반올림 방법을 명시하세요. 테스트 결과에 따라 조정하고 이유를 기록하세요.

실수 모형에 이미 포함한 손실을 여유분에서 중복 차감하지 마세요. 실패한 실행을 통계에서 조용히 제외하거나, 소수의 최적 플레이만으로 HP를 정하지 마세요.

HP는 오프라인 측정으로 산정한 편집 가능한 고정 설정으로 저장하세요. 플레이 도중 결과에 맞춰 몰래 변경하지 마세요.

8. 검증과 완료 기준

기존 테스트를 유지하고, 새 규칙의 핵심 동작을 검증하는 테스트를 추가해주세요.

필수 검증:
- 노트당 한 행동, 정상 Good 입력의 회피·방어 인정
- 방어 효력의 노트 귀속과 중첩 공격 피해 제한
- 페이즈 전환·사망·마지막 노트의 경계 조건
- 카운트다운, Miss, 일시정지, 재시작
- 잡음 생성 실패·접근 불가·생성 한도 문제
- 로그 합계와 결정론적 재현
- Original 및 Special의 편집·선택 기능 회귀

가능하면 최소 1,000개 시드를 자동 검증하고, 조정에 사용하지 않은 별도 시드 집합에서도 결과를 확인하세요. 실행 수와 실패 사례를 보고하고, 표본 통과를 모든 경우의 안전성 증명으로 표현하지 마세요.

실제 Unity 게임 화면에서 다음을 시각 검증하세요.
- 플레이어가 위험 칸에 서 있을 때
- 플레이어 이동 중
- 잡음과 예고가 같은 칸에 있을 때
- 서로 다른 공격 예고가 겹칠 때
- 남은 노트 수가 3→2→1→발동으로 바뀔 때
- 밝은 칸·어두운 칸과 현재 카메라 각도

흰색 빗금, 테두리, 숫자의 가독성과 플레이어 식별을 함께 확인하세요. 코드상 렌더링 순서 확인만으로 시각 검증을 완료했다고 보고하지 마세요.

최종 결과에는 다음을 제출해주세요.

- 구현·수정한 기능과 주요 파일
- 편집 가능한 전투·패턴·생성 설정의 사용 방법
- 시뮬레이션 실행과 로그 재현 방법
- 전략별·페이즈별 행동량 표
- HP 산식, 최종 선택값, 잔여 여유
- 수행한 자동 테스트와 시각 검증 결과
- 남은 문제와 미검증 사항
- 사람 플레이 테스트에서 확인할 재미 평가 항목

실행하지 못한 테스트나 화면 검증은 미검증으로 명시하세요. 자동 시뮬레이션 통과를 사람의 재미 검증 완료로 표현하지 마세요.
