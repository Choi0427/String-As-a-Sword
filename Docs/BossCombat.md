# 보스 전투와 행동 예산 측정

2026-10-22. Unity 6000.5.5f1, Pipeline 0.8.0-exp.1, Unity CLI 1.0.0-beta.14, Codex Unity 플러그인 0.1.8-beta.

## 조사 결과와 적용 범위

- 프로젝트 및 상위 경로에 AGENTS.md가 없었다. 최근 `feat:`, `fix:`, `test:` 형식에 따라 기능별 로컬 커밋을 남겼다.
- 기존 구현은 `ConstantBeatTimeline`의 87 BPM 등간격 노트, 단일 `SongDefinition`이다. Original/Special 채보 파일, 개별 노트 편집기, 채보 선택 UI는 발견되지 않았다. 사용자와 합의한 범위는 **현재 단일 곡의 344개 등간격 노트**와 BPM·노트 수·판정 설정 편집이다. 존재하지 않는 Original/Special 편집·선택 회귀가 통과했다고 주장하지 않는다. 개별 채보 데이터는 생성·변환하지 않았다.
- 이전 방어는 자세만 표시했고 보스 패턴·플레이어 HP·사망·곡 종료 판정이 없었다. 현재 방어·피격·시간 초과 규칙으로 확장했다.
- 분석 전용 구간은 최종 요청한 **1–100 / 101–148 / 149–216 / 217–344**, 행동 기회 **100 / 48 / 68 / 128**이다. 이전 요청의 101–149는 49개이므로 마지막 행동 기회 수를 우선했다. 이 구간은 음악적 구간을 검증한 결과가 아니다.
- 기존 사용자 음원, 1.48초 오프셋, 음량 0.03, 렌더·프로젝트 설정과 삭제 파일을 보존하고 기능 커밋에서 제외했다. 실행·빌드에는 현재 로컬 음원 설정을 사용한다. 음원·개별 노트의 청음 싱크는 별도 사람 검증 대상이다.

## 실행과 설정

`Assets/_Project/Scenes/RhythmPrototype.unity`를 열고 Play → Space/Enter 또는 Start. WASD 한 칸 이동, J 공격, K 방어, R 재시작, Esc 정지, M 클릭음 전환. 홀드는 연속 입력을 만들지 않는다. 시작 위치 D4=(3,3), 공격 행은 최상단 y=7이다.

`Assets/_Project/Data/Songs/GeomEulHyeon87.asset`에서 BPM, Note Count, 음악, Audio Start Offset, 입력·표시 오프셋, Perfect/Good 창과 카운트인을 편집한다. 이번 측정은 87 BPM, 344노트, Perfect ±70ms, Good ±140ms를 사용했다. 공용 전투 코드에 87/344를 고정하지 않았다. 판정창은 기존처럼 박 간격의 45% 이내로 제한한다. 좌우 음표는 같은 한 노트의 거울 표시다.

`Assets/_Project/Data/Stages/FourPhasePrototype.asset` 설정:

공격 피해는 규칙에 따라 최상단에서 1로 고정했다. 적용되지 않는 옛 `Attack Damage` Inspector 항목은 제거했다. 노트 수·HP·수집량·패턴을 바꾼 구성의 공정성/클리어율은 재측정해야 한다. 설정은 전투 생성 시 복사하므로 Inspector를 수정한 뒤 Play를 다시 시작한다.

패턴별 `Enabled`, `Name`, `Kind`, `Coordinate`(0–7), `FirstColumn`, `ColumnCount`, `TelegraphNotes`, `FirstImpact`, `RepeatNotes`, `PhaseMask`를 편집한다. `FirstImpact`는 **해당 페이즈에서 1부터 센 발동 노트**, 반복 간격·예고는 노트 수다. `PhaseMask`는 1/2/4/8 비트의 합(15=전체, 14=2~4페이즈)이다. 예고 길이보다 첫 발동 번호가 커야 한다.

| 기본 패턴 | 범위 | 예고 | 첫 발동 / 반복 | 페이즈 |
|---|---|---:|---|---|
| Row | y=6 행 | 3노트 | 7 / 24 | 전체 |
| Lock | 공개 순간 플레이어 한 칸 고정 | 2노트 | 15 / 24 | 전체 |
| Top | y=7, x=0~3 | 4노트 | 23 / 24 | 2~4 |

Column은 Kind를 바꾸고 Coordinate로 열을 지정한다. 초기 패턴은 전부 방어 가능하며 밀치기가 없다. Top은 안전 칸까지 예고 안에 이동할 수 있는지 검사한다. 새 패턴이 이미 공개된 예고의 안전 칸을 더 이른/같은 발동 시점에 없애면 공개를 한 노트 연기한다. 공개 전 경로 검사는 활성 예고의 합집합을 사용한다. 기존 잡음의 수집·복귀 경로를 막는 공개도 연기한다. 이미 공개된 범위/발동 시점은 바꾸지 않는다. 페이즈 전환 시 이전 예고는 취소하고 새 페이즈의 전체 예고 길이를 확보한다.

## 사건 처리 순서와 종료

1. 인정된 이동은 즉시 논리 위치를 바꾸고 착지 수집한다. 이동·공격·방어 중 한 가지가 노트 행동권을 소비한다. 회피와 수집이 같은 이동이면 한 행동이다.
2. 해당 노트의 Good 창을 **완전히 지난 뒤** 예약된 플레이어 공격을 정산한다. 경계의 늦은 Good 이동·방어도 포함한다. 최상단 밖 J는 행동만 소비하고 피해는 0이다.
3. 그 노트에 발동하는 보스 범위를 합친 뒤 최종 플레이어 위치와 **그 노트의 Guard**를 검사한다. 여러 공격이 겹쳐도 피해는 최대 1. Guard는 위치를 유지하며 피해를 막고 다음 노트로 이어지지 않는다. Miss 자체는 피해를 주지 않는다.
4. 최종 보스를 처치했다면 승리. 마지막 공격과 치명적 피격이 동시에 일어나도 **승리 우선**이다(사용자 선택). 그 외 HP 0은 사망이며, 사망 시 일반 페이즈 전환을 하지 않는다.
5. 살아 있으면 현재 HP 0 AND 수집 목표 완료일 때 다음 페이즈로 전환한다. 잡음과 수집량을 기존 규칙대로 초기화한다.
6. 마지막 노트 판정이 끝났는데 승리/사망이 아니면 시간 초과. 단순 재생 완료는 승리가 아니다. 종료하면 음악과 입력을 멈춘다.

음악 박자는 `BeatScheduler`, 노트 종료는 `RhythmSession.BeatClosed`가 담당한다. 현재 채보는 둘의 간격이 같지만 생성은 음악 박자, 전투·카운트다운은 노트 종료에 귀속된다. 음악 시각을 크게 진행시켜도 이전 판정 종료 → 해당 음악 박자 생성 → 입력의 순서를 유지한다.

## 예고 표시와 실제 화면 검증

보드는 기존 3D 메시 → 전용 카메라 → RenderTexture → uGUI 구조를 유지한다. 바닥 위 어두운 받침(y=.015), 흰 빗금·테두리(y=.023~.024), 플레이어/잡음 3D 메시, 마지막 Canvas의 숫자/연결선 순서다. 64칸 메시와 TMP 배지를 풀링한다. 숫자가 플레이어 실루엣에 걸리면 가까운 빈 배지 자리와 연결선으로 옮긴다.

칸별 숫자와 패턴 목록의 남은 노트는 `ImpactNote - LastClosedNote`. 초기 마지막 완료 인덱스는 -1, 화면 노트 번호는 인덱스+1이다. **1은 다음 노트 판정 종료 시 발동**한다. Miss도 한 번 감소하고 정지 중에는 감소하지 않는다. 중첩은 가장 이른 숫자와 `+N` 추가 예고 수, 발동은 큰 X·테두리·IMPACT로 표시한다. 발동과 다음 예고가 겹치면 `1 X`처럼 함께 표시한다. 색 변화에만 의존하지 않는다.

## 공정한 잡음 후보와 예산

`SafeRoutePlanner`는 (노트 시점, 칸, 수집 비트마스크)의 시간 확장 BFS를 사용한다. 이동은 해당 노트의 합쳐진 공격 범위에 착지할 수 없고, Guard로 한 노트를 안전하게 기다릴 수 있다. 경로는 기존 잡음+새 후보를 수집하고 최상단으로 돌아오는 비용을 함께 센다. 공개 예고가 전혀 없는 구간만 같은 결과의 작은 방문 순열 탐색으로 줄인다. 맨해튼 거리만으로 공격을 무시하지 않는다.

후보는 플레이어·다른 잡음 칸을 제외하고 다음을 만족해야 한다.

`현재 공개 정보의 수집+복귀 비용 + 남은 다른 수집 목표×12 + 실제 남은 보스 HP ≤ 남은 행동 기회`

HP가 아직 정해지지 않은 분석 모드에서는 마지막 보스 HP 항목을 0으로 둔다. 분석의 유효 공격/피해는 공격 가능량 측정용 가상값이며, 실제 게임 HP를 차감하는 실행과 구분한다.

현재 잡음 둘도 **같은 경로에서 함께** 방문할 수 있어야 한다. 수집만 하고 복귀하지 못하는 후보를 버린다. 생성 이후 새 예고 공개도 기존 잡음 경로를 다시 검사하므로 정상적인 공개 과정이 두 잡음을 접근 불가 상태로 만들어 생성 상한을 막지 않는다. 플레이어가 예산을 낭비한 뒤의 모든 선택을 구조하지는 않는다. 미래 미공개 난수·패턴을 조회하지 않으며, 매 단계 공개 정보로 재계획한다.

유효 후보 전체에서 xorshift32-v1의 편향 없는 정수 추출로 하나를 선택한다. 가까운 칸만 고르지 않는다. 이미 나온 잡음은 이동시키거나 만료시키지 않는다. 정규 생성은 기존의 전역 음악 8박 격자(0,8,16,…)이며, 페이즈 전환 직후 첫 생성도 기존대로 다음 음악 박자에 허용한다.

후보가 없으면 다음 음악 박자로 연기한다. 두 번 실패한 뒤에는 인접한 안전 칸을 대상으로 같은 경로·예산 검사를 한다. 대체 후보도 없으면 한 생성 기회당 최대 `interval+2`회까지 연기하고 다음 검사에서 `no-safe-candidate`로 기록해 그 기회를 종료한다(기본값은 10회 연기, 11번째 검사에서 종료). 다음 정규 8박 격자는 옮기지 않는다. 연기 중 새 패턴 공개를 보류해 경로가 풀릴 기회를 준다. 대체 처리도 공격/예산 조건을 무시하지 않는다. 상한이 찬 경우는 `capacity`로 기록하고 밀린 생성을 쌓지 않는다.

탐색 한도는 최대 96노트, 100,000개 상태 확장이다. `SearchLimit`/탐색 실패는 그 제한에서 경로를 찾지 못했다는 뜻이며 불가능성 증명이 아니다. 현재 구성의 미래 난수 전체에 대한 수학적 보증이나 전지적 최적화는 수행하지 않았다. 표본별 실제 공개 정보 전략의 성공률로 확인한다.

## 실행 로그와 재현

실제 입력, 오프라인 전략, 리플레이 모두 `BattleSession`을 호출한다. 전략은 복사된 `BattleObservation`만 받는다. 여기에는 현재 위치/HP/남은 목표/잡음/공개 예고와 총 예산이 있으며 seed, RNG 상태, 미공개 패턴 정의는 없다.

실제 플레이 로그는 `Application.persistentDataPath/BattleLogs`의 JSONL이다. 종료, 재시작, 오브젝트 파괴로 중단된 실행도 저장한다. 정지 상태는 시간을 진행하지 않으며 재시작/종료 시 그 시점까지만 기록한다. 저장 실패는 Console 오류로 알린다. OS 강제 종료·전원 손실의 실시간 로그 복구는 구현하지 않았다.

- header: seed, 채보 식별자 EvenNotes, 타이밍 내용 SHA-256, 전체 설정·설정 해시, 런타임/RNG 버전, 분석 전용 구간.
- input: 원본 노래 시각과 행동/방향. 거부된 입력도 보존.
- event: 예고 공개·연기·취소·발동, 범위의 64비트 16진수 마스크, 음악 박자, 잡음 생성/수집/연기/대체, 피격·방어·페이즈·종료.
- note: 0기반 인덱스, 음악 박자, 행동 전후 위치, 판정, 피해, HP, 수집, 원인, 상호 배타적 분류와 누계, 상태 해시.
- footer: 결과, 처리/남은 노트 수, 정확한 끝 시각, `Completed/Restarted/Interrupted` 사유, 최종 상태 해시. 중단된 실행의 게임 결과는 Running으로 남아 승리/패배와 구분된다.

`처리 노트 = Move + Guard + EffectiveAttack + Other`. Other에는 Miss/대기(`MissOrWait`), 헛공격(`OutOfRange`), HP 하한 공격(`HpFloor`)이 들어간다. 피해와 `attackOpportunity`를 따로 기록하여 HP가 0이라 피해를 주지 못한 공격도 공격 능력에 포함할 수 있다. 자연 대기와 입력 누락은 게임 입장에서는 동일한 무입력이므로 함께 분류하고, 시뮬레이션의 입력 누락 모형은 별도 카운터를 가진다. 끝까지 처리하면 344, 조기 승리/사망/중단이면 실제 처리 수만 센다.

Unity Editor C# 평가로 `StringAsASword.Combat.BattleLog.Replay("로그의 절대 경로")`를 호출한다. `.jsonl.gz`도 지원한다. 설정/채보/버전, 모든 노트 레코드, 처리 수와 최종 상태를 검증하며 불일치 시 예외를 낸다. 시뮬레이션과 실플레이 파일 형식이 같다. 실플레이의 음악 파일 자체는 전투 난수에 관여하지 않으며 타이밍 채보 해시와 구분한다.

## 시뮬레이션과 HP 절차

`StringAsASword.Editor.BattleAnalysis.Run("Logs/BattleCalibration", 1000)`을 Editor에서 호출한다. 긴 실행은 메인 스레드에서 `LoadSettings()` 후 반환 객체를 작업 스레드에 넘겨 `Run(settings, output, count)`를 호출한다. 실행 중 소스 변경, 리컴파일, Play 진입을 피한다. 출력 폴더는 실행마다 새 이름을 권장한다.

```csharp
var settings = StringAsASword.Editor.BattleAnalysis.LoadSettings();
System.Threading.Tasks.Task.Run(() => {
    try {
        var report = StringAsASword.Editor.BattleAnalysis.Run(settings, "Logs/BattleCalibration", 1000);
        System.IO.File.WriteAllText("Logs/battle-full-status.txt", report);
    } catch (System.Exception error) {
        System.IO.File.WriteAllText("Logs/battle-full-status.txt", error.ToString());
    }
});
```

| 전략 | 공개 정보로 선택하는 행동 |
|---|---|
| CollectFirst / 수집 우선 | 안전한 수집·복귀 경로를 우선하고 남은 기회에 공격 |
| AttackHold / 공격 유지 | 급박한 공격은 제자리 방어, 남은 HP·수집·생성 대기 예산이 급해지거나 HP 하한이면 수집 |
| MovementUse / 이동 활용 | 평상시 짧은 수집 경로, 위협 시 수집과 회피를 결합, 예산이 급하면 긴 경로도 사용 |

가상 구간에서 각 전략의 공격 가능량을 기록한 뒤, **CollectFirst를 기준 전략**으로 페이즈별 하위 10%를 구한다. 오름차순 표본의 `ceil(0.1×N)`번째인 nearest-rank 분위수를 사용하고, `HP = floor(P10×0.875)`로 12.5% 여유를 둔다. 미방문/실패 구간의 0도 제외하지 않는다. HP<1이면 임의로 올리지 않고 후보 산정을 실패로 보고한다.

이 후보로 실제 HP·수집 AND 전환을 적용해 전곡을 재실행한다. 기준 전략 90% 이상 성공이면 멈춘다. 부족하면 수집을 끝냈는데 HP만 남은 시간 초과 페이즈에 한해 최대 10%씩, 최대 8회 보정한다. 사망·수집 실패를 숨기거나 무조건 HP를 깎지 않는다. 가상 구간은 실제 플레이의 강제 전환에 들어가지 않는다.

조정용 seed 0–999와 별도 seed 100000–100999를 사용한다. 별도 집합은 HP 조정에 사용하지 않는다. 별도 집합의 입력을 5% 확률로 누락시키는 민감도 실험도 수행한다. HP 산정 모형은 입력 누락 0%이므로 12.5% 여유에서 누락 손실을 다시 차감하지 않는다. 입력 누락 RNG는 전투 난수와 분리되어 있다.

출력 `phase-samples.csv`는 실패/미방문까지 포함한 모든 페이즈, `phase-distributions.csv`는 min/P10/P50/P90/max/평균, `run-diagnostics.csv`는 생성/패턴 연기와 불변식 실패, `logs/*.jsonl.gz`는 모든 실행, `calibration-iterations.txt`와 `health.txt`는 보정 이력·HP다. 전환 노트 CSV는 0기반이며 -1은 미전환, 보고서의 사용자 노트 번호는 +1이다.

검증 보고서: [EditMode](BattleValidation/editFinal.json), [PlayMode](BattleValidation/playFinal.json), [빌드](BattleValidation/windows-build-report.json), [실행 파일 진단](BattleValidation/standalone-verification.json), [실행 파일 보드 렌더](BattleVisual/standalone-board.png). 마지막 이미지는 카메라 렌더라 HUD 검증 근거로 사용하지 않았다. 최종 통합 ponytail-review는 이번 커밋·변경 파일, 호출부, 설정, 테스트와 문서 수치를 대조했고 추가 재현 가능한 must-fix는 발견하지 못했다.

표본 통과를 모든 시드/임의 설정에 대한 안전성 증명으로 표현하지 않는다. Original/Special 데이터·선택 UI 회귀, 새 개별 노트 편집기, OS 강제 종료 로그 복구, 목표 기기의 프레임 프로파일링, 다른 해상도/카메라 각도의 전수 검증, 전곡 청음 싱크와 사람 플레이의 재미는 미검증/범위 밖이다. 사람 플레이의 재미를 자동 시뮬레이션으로 완료 처리하지 않는다.

사람 플레이에서 확인할 항목: 최상단을 지키는 방어와 수집 이탈의 선택이 의미 있는지, 2~4노트 경고를 음악과 함께 읽을 수 있는지, 이동·수집 겸용 행동이 보상처럼 느껴지는지, HP3 실험값과 5% 누락 이후 회복 여지가 적절한지, 짧은 2페이즈가 충분한 패턴 학습 시간을 주는지, 예고 숫자·말 실루엣·파형이 작은 해상도에서도 읽히는지, 실제 음원과 전곡 노트 싱크 및 344번째 종료가 자연스러운지.

## 사용한 스킬

| 스킬 | 실제 적용 |

| unity | unity-cli·playmode-verification-loop·UI·uGUI 가이드 확인. 버전/프로젝트 연결, 컴파일→Edit/Play 테스트, 기존 카메라·RenderTexture 유지, TMP/Canvas 순서 및 실제 Game View 검증 |

| ponytail-review | 이번 기능 커밋과 변경 파일의 호출부·설정·테스트까지 검토. 설정 상한 불일치, 미사용 피해량 설정, 중단 로그 경계와 UI HP 표현을 수정하고 재검증 |
