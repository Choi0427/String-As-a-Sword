## 1. 검증용 채보 배치

- 경고 = 후보 파일의 최소 경고 + 1(최소 1). 그래서 실제 경고는 1~3이에요.
- 첫 공개는 노트 8이에요. 플레이어가 공개 전에 d4에서 판 어디로든 걸어갈 수 있게 했어요.
- 다음 공격은 앞 공격의 발동 노트 + 2 이상에서 공개돼요. 그래서 공격끼리 겹치지 않아요.
- 빠른 구간 91–98, 201–208에는 공개·경고·타격이 걸리지 않아요. 공개 노트도 이 구간 밖이에요. 90·200번 타격도 피했어요. 마지막 타격은 225예요.
- 모양마다 `section 이름 공개-발동`을 달았어요. 노트 대응표는 6절 표의 "공개–발동 / 경고" 열이에요.

## 2. 검증기

메뉴 **Validate**는 모달 대화상자를 띄워 MCP 호출을 막아요. 그래서 메뉴와 같은 코드인 `BossChartValidator.Run(path, 0)`을 에디터 C#으로 호출했어요. 결과 파일 `validation.txt`는 `phase1-validation.txt`로 옮기고 원래 파일은 되돌렸어요.

- 검증용 채보: **통과. 공격 48개 중 실패 0, 경고 0.**
- 최소 경고: 모양 하나만 든 임시 채보(노트 20에 공격)로 경고 1부터 올리며 `BossChartValidator.Check`를 돌렸어요. Python 값과 다른 모양은 없어요.
- 경고를 하나 줄이면 실패하는 출발 칸(검증기 표기 `(줄,칸)`을 체스 칸으로 바꿈):

## 3. 조합 검사

후보 파일 머리말의 예시 시퀀스를 노트 0–56에 실제 번호로 놓았어요. 노트 0–38은 모두 한 박 간격이에요(39, 54, 67, 68, 73, 74번 앞이 두 박).

| 조합 | 배치(발동 노트 / 경고) | 검증기 | 인게임 |
|---|---|---|---|
| 폰 전진 4연속 | 폰줄-7 3, 폰줄-6 7, 폰줄-5 11, 폰줄-4 15 / 3 | 통과 | 통과(폰줄-7의 1칸 확인 1건은 공개 노트가 0이라 미리 걸어갈 수 없어 해당 없음. 같은 모양은 검증용 채보에서 확인) |
| 비숍 흰칸·검은칸 교대 | 흰 20, 검 21 / 2 | 통과 | 통과 |
| 비숍 4연 교대(추가) | 흰 24, 검 25, 흰 26, 검 27 / 2 | 통과 | 통과 |
| 오프닝 4연속 | 33, 37, 41, 45 / 3 | 통과 | 통과 |
| 전체 hits=2 every=2 | 50, 52 / 2 | 통과 | 통과. 가드 전용으로 공개되고, 두 번 모두 가드 성공, 대기하면 두 번 모두 피격 |
| 핀 | 56 / 2 | 통과 | 통과(d4·a4·d8·h1) |

간격 여유도 확인했어요. 폰 전진과 오프닝을 1·2·3·4노트 간격, 경고 1·2·3으로 바꿔도 모두 통과해요. 비숍 교대는 경고 1·2·3 모두 통과하고, `전체` 2연타는 경고 1·2, every 1·2 모두 통과해요. 검증기는 노트 번호로만 검사해요. 그래서 "한 박 간격일 때만 성립"이라는 조건은 채보 작성 규칙으로 지켜야 해요.

## 4. 인게임 판정

`Phase1PatternVerification`이 공격마다 실제 `BattleSession`을 새로 만들어요. 설정은 프로젝트 곡·스테이지 설정을 복사해 `BossChartText`를 넣은 것이에요. `SpawnInterval` 100000, `PlayerMaxHp` 1000이고 에셋은 저장하지 않아요. 입력은 실제 이동·가드 요청을 노트 시각 정각에 넣어요.

확인 항목(모든 확인에 공통):

- `pattern-publish`의 칸 마스크가 그림에서 직접 계산한 기대값과 같아요. 1칸은 Either, 2칸은 DodgeOnly, 판 전체 1은 GuardOnly예요. 추적 모양은 공개 순간 위치로 옮기고 잘라요. 기대값 계산은 런타임 `BossChart.Cells`와 별개로 구현했고, 48모양 × 64칸에서 런타임과 일치했어요.
- 공개 노트 = 발동 노트 − 경고, 이벤트의 `warningNotes` = 경고.
- 카운트다운(`Remaining`)이 공개 직후부터 경고, …, 1로 줄어요.
- 발동 노트에 `pattern-fire`가 공개한 수만큼 나오고, `pattern-skip`과 `pattern-cancel`은 없어요.
- 발동 노트의 응답 이벤트와 HP 변화:

| 상황 | 기대 |
|---|---|
| 1칸에서 가드 | `guard-success`, HP 그대로 |
| 2칸에서 가드 | `guard-broken` + `player-hit`, HP −1 |
| 1칸·2칸에서 대기 | `player-hit` 한 번, HP −1 |
| 안전 칸에서 대기 | 이벤트 없음 |
| 플레이어 칸이 0인 추적 모양에서 발동 노트에 옆 칸으로 이동 | 옆 칸이 공격 칸이면 `player-hit`, 아니면 없음 |

출발 칸: 맵 고정 모양은 각 종류(1칸/2칸/안전칸)에서 d4에 가장 가까운 칸으로 공개 전에 걸어가요. 추적 모양은 **d4(중앙), a4(왼쪽 가장자리), d8(최상단), h1(구석)** 네 곳에서 공개해요. 그다음 경고 안에 닿는 가장 가까운 칸에서 확인해요.

변이 검사로 fixture가 틀린 기대를 잡아내는지도 확인했어요. 앵커를 한 칸 어긋나게 하면 "칸 다름"으로 실패하고, 강공격 칸에서 가드 성공을 기대하면 "결과 guard-broken+player-hit"로 실패해요.

"해당 없음" 20건은 모두 구조상 생기는 것이에요.

- 비숍X중심강 1칸(4곳): 대각선 1칸이 두 걸음 거리인데 경고 2로는 한 걸음만 가고 가드해야 해요.
- 킹고리·나이트훈수 1칸, 킹고리강·나이트훈수강 2칸(각 4곳): 경고 1이라 발동 전에 움직일 수 없어요. 대신 발동 노트 이동으로 확인했어요.

## 7. 발견한 문제와 주의

버그 수정은 하지 않았어요. 모두 보고만 해요.

**주의 1. `anchor=4,4` 추적 직선이 판 끝까지 닿지 않아요(설계 주의).**
`룩가로`·`룩세로`·`룩세로강`·`룩3열`·`비숍X추적`·`비숍X중심강`은 앵커가 4번째 줄 = d5에 그려져 있어요. 옮긴 뒤 잘리므로, 플레이어가 5랭크가 아니면 세로줄·대각선 한쪽 끝이 빠져요. 시작 칸 d4에서도 `룩세로`는 d8, `룩3열`은 c8·d8·e8, `비숍X추적`은 h8이 빠져요. 64칸 중 "플레이어 열·행·대각선 전체"와 정확히 같은 칸은 `룩가로` 8칸(d열), `룩세로`·`룩3열` 8칸(5랭크), `비숍X추적` 7칸뿐이에요. `앞길막기`류는 1~3랭크에서 8랭크까지 닿지 않아요. 8×8 그림을 옮기는 방식의 한계예요. 판 전체 직선이 필요하면 15×15 그림이나 직선 전용 표기가 필요해요. 후보 파일 머리말의 "가장자리에 있으면 긴 줄이 짧아져요"는 이 효과를 덜 말해요.
재현: `BossChart.Cells(룩세로, d4)` → d1–d7. 테스트 `AnchoredShapesMoveAndClipAtTheEdges`.

**주의 2. `비숍X중심강`의 1칸은 경고 2에서 쓸모가 없어요.** 대각선 칸이 플레이어에게서 두 걸음이라 발동 때 그 칸에 있을 수 없어요. 실제 플레이는 `핀강`과 같아요.

**주의 3. `나이트훈수`·`나이트훈수강`은 경고 1~2에서는 맞을 수 없어요.** L칸은 플레이어에게서 세 걸음이에요. 인계 문서의 "0칸 회피 모양(킹고리·나이트훈수 계열) → 주변 칸으로 이동하면 피격"은 **킹고리 계열에만 맞아요.** 나이트훈수 계열은 옆 칸으로 움직여도 안전한 것을 인게임으로 확인했어요(테스트 `KingRingPunishesAnyStepButKnightAdviceCannotReach`). 또 경고 1에서는 발동 전에 움직일 수 없으므로 `킹고리강`의 2와 `킹고리`의 1은 플레이상 차이가 없어요.

**주의 4. 플레이어 칸의 2가 화면에서 1과 구분되지 않아요(가독성).** 2칸의 주황 테두리·화살표 표시가 나이트 모델 바로 아래에 그려져 가려지고, 옆 배지는 숫자만 보여 줘요. [핀강 캡처](phase1/strong-pin-d4-2.png)에서 d4는 숫자 `2`와 플레이어 테두리만 보여서 `핀`(가드 가능)과 구분이 안 돼요. `킹손바닥강`도 같아요. 플레이어 칸이 2인 모양은 `비숍X중심강`·`킹손바닥강`·`핀강`이고, `룩세로강`·`앞길막기강`도 2가 플레이어 칸에 걸리면 해당돼요. 배지에 응답 종류(MOVE)를 함께 보여 주는 등 표시 수정이 필요해 보여요.
**→ 해결(battle-7):** 카메라 각도로는 고칠 수 없었어요. 실제 카메라는 ArtSet의 35°이고, 표시가 받침대와 외곽선 밑에 있어 90°에서도 가려져요. 대신 배지 배경을 응답 색으로 칠했어요(회피 필수 주황, 가드 전용 파랑, 일반은 그대로). 플레이어 칸이 경고받으면 외곽선도 그 색으로 바뀌어요. 확인: [핀강 d4](phase1/fixed-strong-pin-d4-2.png), [전체 가드](phase1/fixed-guard-full-d4-2.png).

**문서 오류: "첫 줄 = 플레이어가 시작하는 줄".** 실제 시작은 (3,3) = d4(그림 5번째 줄)예요(`BattleSession` 생성자). 고치지 않고 위치만 적어요.
- `Docs/BossChart.md` "모양" 절: "첫 줄이 판의 맨 윗줄(플레이어가 시작하는 줄)이에요."
- `Assets/_Project/Scripts/Combat/BossChart.cs` 클래스 주석: "the first line is board row y = 7, the player's start row."
- `Assets/_Project/Data/Bosses/GeomEulHyeon.bosschart.txt` 주석: "첫 줄이 판의 맨 윗줄(플레이어 시작 줄)이에요."

**로그 표기: `pattern-fire`의 `noteIndex`가 발동 노트 − 1이에요.** `Resolve(note)`가 `LastClosedNote`를 갱신하기 전에 이벤트를 남겨서 그래요. `impactNote`는 정확하고, 응답 이벤트(`player-hit` 등)의 `noteIndex`는 발동 노트예요. 판정에는 영향이 없어요. 로그를 읽는 도구는 `impactNote`를 써야 해요.
재현: 검증용 채보로 세션을 만들고 노트 11까지 진행 → `pattern-fire noteIndex=9 impact=10 폰줄-7`.

**인계 문서와 다르게 한 것.**
- Validate는 메뉴 대신 같은 코드(`BossChartValidator.Run`)로 실행했어요(모달 대화상자 때문).
- `capture_game_view`의 `save_path`는 `Assets/` 아래에만 저장돼요. 그래서 `Assets/Docs/…`에 저장한 뒤 `Docs/BossChart/phase1/`로 옮겼어요.
- 공개 노트도 빠른 구간 노트에 두지 않았어요(검증기는 공개 노트 자체는 허용해요). 그래서 나이트-f3 이후 배치가 1노트씩 뒤로 밀렸어요.
